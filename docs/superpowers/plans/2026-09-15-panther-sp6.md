## Context

`docs/` in this repository carries three incompatible meanings at once:

- **mkdocs source** — `mkdocs.yml` declares neither `docs_dir` nor `site_dir`, so mkdocs
  defaults to `docs/` as source and `site/` as output.
- **generated output** — PANTHER's real source is `docs_src/`; `_build_documentation`
  assembles `docs/` from it.
- **tracked corpus** — 38 tracked files live there: 31 plans under
  `docs/superpowers/plans/`, 5 specs under `docs/superpowers/specs/` (including the
  one-door design that governed CLI-1/2/3 and the draft-quality spec governing the SP7d
  work running concurrently), and 2 under `docs/research/`.

Because of the overload, five code paths delete or revert tracked work. All five are
measured in this tree, not inferred:

| # | Site | What it destroys |
|---|------|------------------|
| 1 | `panther/cli/commands/docs.py:61-64` | `for dir_name in ["docs", "site"]` → rmtree |
| 2 | `panther/cli/commands/docs.py:82-85` | second, redundant `shutil.rmtree(docs_dir)` |
| 3 | `panther/cli/commands/build.py:31` | `dirs_to_clean = [... "docs" ...]`, 4 call sites |
| 4 | `panther_builder.py:57` | standalone copy of the same list |
| 5 | `panther/cli/commands/docs.py:48-54` | copies tracked `mkdocs.yml.bak` over `mkdocs.yml` |

Sites 1 and 2 are both reached from three commands (`docs build` `:268`, `docs serve`
`:288`, `docs deploy` `:318`). Site 3 is reached from four (`build.py:222`, `:248`,
`:270`, `:313`). Site 4 is reached from `panther_builder.py:127` (`clean`, which
**never forwards to the CLI** — `main()` handles it directly before
`_try_forward_to_cli`) and `:142` (`package-dev` bootstrap). So fixing only the CLI
leaves the bootstrap path fully destructive.

Site 5 is destruction outside `docs/`: `panther/tools/docs_gen/mkdocs.yml.bak` is
tracked, present on disk, dated Jul 28, and differs from the live `mkdocs.yml` by
exactly one line — live `mkdocs.yml:78` carries
`- ai_rfc (reconstructed specs): reference/ai_rfc.md` and the backup does not. One
`panther docs build` silently reverts that tracked line.

**Why it has survived.** `.gitignore:54` holds a bare `docs/`, so *new* files there are
ignored (hence every plan commit in this project needing `git add -f`), while the 38
already-tracked files stay tracked — ignoring never untracks. The wipe therefore shows
as 38 deletions in `git status` and is recoverable with `git checkout`, but it is
invisible in advance.

**Why it is about to stop being recoverable.**
`.github/workflows/pr-generate-docs.yaml` runs, on every PR to `production`:
`panther docs build` (`:33`) → `mkdocs build --strict` (`:36`) →
`git-auto-commit-action@v4` (`:37-41`, no `file_pattern` set, `contents: write`) →
`mkdocs gh-deploy --force` on push (`:44`). Deletions of tracked files are staged
regardless of ignore rules, because ignore rules govern only untracked files.
*Unverified external claim, flagged as such:* that the action's default `file_pattern`
is `.` was not tested from here — no network. The severity argument does not rest on the
exact default, only on the action staging with add-all semantics, which is its documented
purpose. Confirm before quoting the default to anyone.
`origin/production` currently has **zero**
tracked files under `docs/` (they were untracked in `062ab453e`), so the 38 exist only on
this branch — but when this branch opens its PR to `production`, CI would commit all 38
deletions into it automatically.

**Intended outcome.** Neither build path can delete or revert tracked work, demonstrated
by observation in a throwaway clone that reproduced the destruction first.

## Decision: Option B — separate generated output from tracked corpus

Approved by the user at the Phase 2 stop. `docs/` becomes corpus-only and is never
touched by any build path; generated output moves to a new `docs_build/`, declared to
mkdocs as `docs_dir`.

Rejected: Option A ("refuse to delete anything git tracks"). It is the better-shaped
predicate in the abstract, but measured against this tree it loses on four counts:

1. It does not save the two **untracked-and-ignored** files already living in the corpus
   directory — `docs/superpowers/plans/2026-09-05-arfc-gepa-no-key-executor-prompt.md`
   and `2026-09-09-arfc-sp-closure-executor-prompt.md`. A tracked-path predicate deletes
   them silently and irrecoverably. B protects them.
2. It creates a **new publication exposure**. `mkdocs.yml` has an explicit `nav` but no
   `exclude_docs`, and mkdocs renders every `.md` under `docs_dir` whether or not it is
   in the nav. **Measured, not assumed** (2026-09-15, this repo's `.venv/bin/mkdocs`
   1.6.1, throwaway project under `/tmp/claude-501/sp6/review/mk/`): a `docs/` tree whose
   `nav` listed only `index.md` still built
   `site/superpowers/plans/secret.html` containing the page's full text. Today the corpus
   is deleted *before* mkdocs runs, so it never ships; if it survives in `docs_dir`,
   `gh-deploy --force` publishes 31 internal plans and 5 specs to the public GitHub Pages
   site. Patching that needs an `exclude_docs` enumeration — a third list to keep in sync.
3. It leaves `.gitignore:54` in place, so the `git add -f` tax every row of this project
   has paid continues.
4. The bootstrap path would need a stdlib-only shared git-predicate helper. Possible
   (`panther/__init__.py` and `panther/tools/__init__.py` are both stdlib-clean), but
   more surface than a constant.

**What B costs if wrong:** anything external that reads generated `docs/` breaks. Priced
by grep — the consumers are `MANIFEST.in:12` (`recursive-include docs *`) and `:16`
(`prune docs/site`), `tests/pytest.ini:norecursedirs`, and lint excludes in
`pyproject.toml:319` (`[tool.bandit] exclude_dirs`) and `:408` (`[tool.pyright] exclude`
— **not** vulture). All are repointed by Task 5. CI
(`pr-generate-docs.yaml`) calls only `panther docs build` and `mkdocs ... --config-file
mkdocs.yml`, both of which follow the config, so CI needs no edit.

**Directory name:** `docs_build`. Verified free — the only `docs_build` in the tree is
the Python function `docs.py:257`, unrelated. Not `docs_gen`, which would collide with
the existing `panther/tools/docs_gen/` module.

## Rulings

Numbered, with what each costs if wrong. Carried into the row's deviation log.

- **R1 — One shared constant, three consumers.** The clean list is defined once in a new
  stdlib-only `panther/tools/build_paths.py` and imported by `build.py`, `docs.py` and
  `panther_builder.py`. Four copies of a directory list is what let sites 1 and 4 escape
  the brief's own inventory. *Cost if wrong:* the bootstrap import fails in an
  environment where the repo root is not on `sys.path`, breaking `panther_builder.py`
  before anything is installed. Mitigated by Task 2's test and by letting the import fail
  loudly rather than falling back to a hardcoded list — a silent fallback would
  reintroduce the defect.
- **R2 — Remove the mkdocs backup/restore dance entirely** rather than repair it. It
  protects against nothing git does not already protect, and under B it is load-bearing
  in the wrong direction: left in place, the first `docs build` copies the stale Jul 28
  backup over `mkdocs.yml` and reverts the `docs_dir` declaration, silently undoing the
  whole row. *Cost if wrong:* someone depended on `.bak` as a recovery artifact; the file
  is in git history, so recovery is `git show`.
- **R3 — Sites 1 and 2 collapse into one deletion step.** `docs.py` deletes the same
  directory twice in one function; the extracted `_reset_generated_output` does it once.
  *Cost if wrong:* nothing — the second rmtree is unreachable-after-the-first by
  construction.
- **R4 — CI is reported, not edited.** `.github/workflows/` is outside the assigned file
  list, and once the destroyers are fixed the auto-commit has no deletions to commit, so
  the chain is defused at its source. *Cost if wrong:* a future destroyer reappears and
  CI again commits deletions. Goes in the For-the-user list.
- **R5 — The mkdocs config test uses a tag-tolerant YAML loader, not `yaml.safe_load`
  and not regex.** Measured: `safe_load` raises `ConstructorError` on `mkdocs.yml:97`
  (`!!python/name:pymdownx.emoji.twemoji`; four such tags at `:97`, `:98`, `:103`,
  `:118`). `mkdocs.config.load_config()` is the semantic alternative but instantiates
  plugins, and `SameDirPlugin.__init__` monkeypatches
  `mkdocs.config.config_options.Dir.post_validation` process-wide — a side effect leaking
  into other tests. *Cost if wrong:* the config test passes on a malformed config.

### Harness constraints the verification procedure must obey

Two blockers measured this session. Both would stop Task 1 at its first command if the
plan did not name them.

**C1 — the worktree guard refuses scripted git.** A command that names `git` with a
variable, inside a compound construct, or with a runtime-computed target is refused
outright: *"this command names git in a form too complex to verify that it stays inside
the worktree. Refusing to run it."* Measured against `git clone --quiet "$SRC" clone`
inside a `set -e` script. The same clone succeeded as a plain single command with a
literal absolute path. **Every git command in Task 1 and in the Phase 4 gate must
therefore be a separate, plain invocation with literal absolute paths** — no `$VAR`, no
`&&` chains around git, no heredocs, no loops. Non-git commands (`find`, `ls`, `wc`) may
still be combined.

**C2 — the clone supplies data; the worktree supplies code.** `.venv/bin/panther` is an
editable install resolving to this worktree (measured: `import panther` →
`<worktree>/panther/__init__.py`). Running it with the clone as cwd means
`find_project_root()` returns the clone, so **the worktree's code executes against the
clone's tree**. Two consequences, both load-bearing:

- Task 1's reproduction must complete **before any implementer edits a source file**.
  Once Task 2 lands, a "reproduction" would silently exercise partly-fixed code and prove
  nothing.
- `git clone` carries **committed state only**. The Phase 4 gate must therefore run only
  after every task is committed; otherwise the clone's `mkdocs.yml` and `.gitignore` lag
  the worktree's fixed code and the gate returns a false result in either direction.

Verified this session: cloning the worktree with
`git clone --no-recurse-submodules <worktree> /tmp/claude-501/sp6/review/clone` produced
branch `feat/arfc-pipeline-and-runtime-anchors` with **38 tracked files under `docs/`
checked out on disk** — tracked files are checked out despite `.gitignore:54`, which is
what makes the reproduction possible. Both submodule directories come out present and
empty (0 entries).
